# C4 功能测试用例

> 本文件记录 C4 的功能测试用例，每条用例说明：**测试输入**、**测试特性**、**曾经出现的问题**、**修复的版本**。
> 用例对应「曾经暴露的缺陷」，用于缺陷修复后的回归验证。

---

## 用例 1：用户文本描述 ASFP2 接入与转发信息（内容齐全）✅

- **测试特性**：用户通过一条文本一次性提供全部接入信息——设备与协议、10 个点的「地址:点名」、接收监听端口（9001）、转发目标（127.0.0.1:9900）与转发点表（5000~5009）
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，目标地址是127.0.0.1:9900，点表5000~5009。
```

> 关键点：点名、接收端口、转发目标、转发点表全部由用户提供，系统必须**原样采纳**——
> 不得自行编造转发地址、不得改动用户指定的端口，方案摘要须逐条列出「地址 ↔ 点名」映射与接收/转发端口供核对。

### 曾经出现的问题

C4H1 之前：转发点业务字段（addr）未采纳用户提供值，而是被系统自动编造（从 3001 起顺序编址）；
用户指定的接收端口在执行阶段未正确传递（`output_plan_steps` 首次调用因缺 ip/port 校验失败后重试）；
方案摘要不展示端口，用户无法核对。修复后：用户提供的点表、端口、转发点表原样进入 config.json。

## 用例 2：消息含与配置场站一致的场站名（归属校验）✅

- **测试特性**：条件完整，消息中的场站名「华能阿拉善风电场」与 agent.json 配置的场站「华能阿拉善」一致；用户文本完整描述接入与转发信息（点名、接收端口 9001、转发目标 192.168.110.3:9900、转发点表 5000~5009）
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入华能阿拉善风电场1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，目标地址是192.168.110.3:9900，点表5000~5009。
```

> 关键点：消息带场站前缀「华能阿拉善风电场」，与当前场站一致 → 归属校验通过，直接接入；
> 不得因场站信息再次询问，也不得误判为「不属于当前场站」。

### 曾经出现的问题

C4H1 之前：LLM 在场站已设置的情况下仍反复询问场站名称与缩写（提示词两分支规则遵从性差，
且系统提示残留未替换的 `{{ current_site }}` 占位符，被模型解读为「场站未设置」）；用户另给场站名
（如「开鲁」）时被照单全收，违反「实例绑定唯一场站」。修复后：场站归属校验确定性执行——
场站已绑定时禁止询问，消息含一致场站名 → 直接接入，含其他场站名 → 回复「该资料不属于当前场站」。

## 用例 3：消息含与配置场站不同的场站名（归属拒绝）✅

- **测试特性**：条件完整，但消息中的场站名「华能通辽风电场」与 agent.json 配置的场站「华能阿拉善」**不同**；其余接入信息（点名、接收端口 9001、转发目标 192.168.110.3:9000、转发点表 5000~5009）齐全
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入华能通辽风电场1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，目标地址是192.168.110.3:9000，点表5000~5009。
```

> 关键点：一个 C4 实例绑定唯一场站。消息场站与当前场站不同 → 必须回复「该资料不属于当前场站」并停止：
> 不得接入、不得生成方案、不得切换场站，即使其余接入信息完整也不例外。

### 曾经出现的问题

C4H1 之前：LLM 在场站已绑定时仍反复询问场站信息；用户另给场站名（如「开鲁」）时被照单全收并完成接入，
场站被静默切换，违反「实例绑定唯一场站」。修复后：场站归属校验确定性执行——
消息含其他场站名 → 直接回复「该资料不属于当前场站（当前场站：X）」并停止，不调用任何工具。

## 用例 4：转发点表描述模糊，Agent 多次询问与推断后接入（升压站）✅

- **测试特性**：新设备类型（升压站）；接收点表用「:」与「是」两种混述的松散文本给出（非表格）；**转发点表描述模糊**——仅说「点表与I区一致」，未逐点给出转发地址；Agent 通过多次询问与推断确定转发点表后接入成功
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入升压站的数据，第三方厂家转过来的，asfp2协议，2390:电网频率，2391是正向有功，2392是反向有功，2393是正向无功，2394是反向无功，2395是uab，2396是ubc，2397是uac，2398是变压器油温，2399是环境温度。II服务器地址是192.168.110.3:9000，点表与I区一致。
```

> 关键点：转发点的 addr 是必要项，但用户仅以「与I区一致」的等价描述给出——Agent 必须通过
> 询问/推断明确每个转发点的地址（2390~2399 一一对应），**不得自行编造**；接收点表的松散文本
>（「:」与「是」混述）应被正确解析为 10 个点。

### 曾经出现的问题

C4H1 之前：转发点业务字段缺失时被系统自动编造（3001 起顺序编址），用户提供的等价描述
（「点表与I区一致」）无法被采纳。修复后：必要项缺失时 Agent 逐项询问，结合用户回答与接收侧
点表推断出转发点表（2390~2399 一一对应），多次交互后接入成功。

## 用例 5：未提供转发点表，用户以自然语言给出起始地址（升压站）✅

- **测试特性**：新设备类型（升压站），接收点表与用例 4 相同（2390~2399）；**未提供转发点表**，Agent 询问后用户以自然语言给出起始地址（「接收端口使用7867，转发地址/转发点表使用从一万开始的地址」，即转发 addr = 10000, 10001, …）
- **修复的版本**：C4H1——**经五轮迭代修复（见多轮测试记录与两节附录），2026-09-01 22:47 复测全链路通过**：
  Agent 先询问端口 → 7867 全程保持（摘要/工具参数/config.json/实际监听）→ 按钮确认执行 →
  服务监听 7867、采集/转发各 10 点；转发侧 192.168.110.3:9000 为用户显式指定，语义正确

### 测试输入

```
现在需要接入升压站的数据，第三方厂家转过来的，asfp2协议，2390:电网频率，2391是正向有功，2392是反向有功，2393是正向无功，2394是反向无功，2395是uab，2396是ubc，2397是uac，2398是变压器油温，2399是环境温度。将数据转发到II服务器的192.168.110.3:9000上。
```

Agent 询问缺失信息后，用户补充回答：

```
接收端口使用7867，转发地址使用从一万开始的地址。
```

> 关键点：转发地址以**起始地址**的自然语言形式给出（「从一万开始」），Agent 应将其展开为
> 逐点 addr（10000~10009）并成功通过 `output_plan_steps` 生成配置。

### 多轮测试记录（C4H1）

| 轮次 | 修复状态 | 结果 |
|------|---------|------|
| 第一轮 | 初版 | ❌ Agent 陷入 `output_plan_steps` 反复失败重试循环（自省文字不断调整转发点对象结构：addr 位置、属性、字段顺序），接入失败。根因：转发点输入 schema 复用采集点定义，误要求 `name` 必填字段，无 name 的转发点被 Zod 校验拒绝 |
| 第二轮 | 修复①（校验错误可读化：带设备/点序/字段上下文）+ 修复②（点表完整性拦截：协议可判定时采集点必须逐点含业务字段） | ⚠️ 接入可用但不稳定：同一输入序列多次测试，LLM 传参**概率性丢失端口**——一次 7867 正确落地，一次被 registry 默认值 9000 静默覆盖（LLM 回复文本中复述了 7867，工具调用参数却未携带） |
| 第三轮 | L2 执行闸门（未经用户确认不执行）部署后 | ⚠️ 接入成功，但 **Agent 未询问确认**——用户回答「…从一万**开始**…」中的「开始」命中宽松确认正则，被状态机直接判定为已确认后放行执行 |
| 第四轮 | 按钮唯一确认通道部署后 | ⚠️ 方案摘要正确列出 7867，点按钮后 `output_plan_steps` 前两次因转发目标缺 ip/port 被可读校验拦截，**第三次重试 LLM 重建参数时把端口回退为 registry 默认 9000**（最终回复仍宣称 7867）。根因：端口仅存在于对话文本，确认轮注入的 deviceInfo 是端口回答**之前**抽取的（不含端口），重试时 LLM 手边只有提示词默认值 |

### 待决问题：用户确认方式 → 已定稿：Web 按钮为唯一确认通道

自由文本确认识别存在不可消除的歧义：参数回答与确认表达在文本上重叠（「从一万**开始**」命中确认词
「开始」）时，确定性状态机无法区分「提供信息」和「表达确认」——宽松正则下偶发跳过确认询问
（第三轮），收紧正则又会误拦正常确认（曾在第二/三轮间试验后移除）。

**定稿方案（已实现）**：使用 Web 技术确定用户确认方式——**用户点击按钮决定确认还是取消，
非按钮发送的内容一律不视为用户确认信息**：

- 前端 `ConfirmButtons`（方案展示句式触发展示）点击「确认」发送结构化消息
  `[C4_BUTTON_CONFIRM] 确认`，点击「取消」发送 `[C4_BUTTON_CANCEL] 取消，不执行`
- 后端执行闸门仅识别 `[C4_BUTTON_CONFIRM]` 前缀消息置位「已确认」；自由文本中的确认词
  （确认/好的/执行/开始等）不再构成确认，「从一万开始」类参数回答不会再误触执行
- 未确认时闸门拒绝执行，并提示用户点击「确认」按钮
- 协议契约记录于 web.md §3.1.3（按钮驱动）与 agent.md「执行闸门」，前端
  `useConfirmDetect.ts` 常量与后端前缀修改时必须两侧同步

### 第四轮修复：端口确定性捕获与注入（2026-09-01）

- **super_worker.ts**：新增 `userPort` 状态——从用户消息确定性捕获显式指定的接收端口
  （正则 /(?:接收|监听)?端口…(\d{4,5})/，同场站名解析机制），确认轮注入
  「用户指定的数据接收端口: NNNN（必须原样使用，禁止改为默认端口）」，执行完成后复位
- **system.txt 解耦回归**：撤销曾硬编码的「默认接收端口 9000」字样——默认端口属于 asfp2
  MCP 注册 JSON 的 prompt_hints（运行时拼接），system.txt 保持服务中立，仅要求
  「写出具体数字、禁止含糊表述」并强调用户指定端口必须原样使用

### 设计变更：端口必填，无默认值（2026-09-01，用户裁定）

捕获+注入仍属概率性防线（LLM 仍可能忽略注入指令回退默认值）。据此将设计改为**釜底抽薪**：

- **不设置默认端口**：registry `c4_asfp2_server.json` 移除 `port` 默认值，`config_schema.required`
  声明 `["port"]`，prompt_hints 改为必填语义
- **Agent 强校验**：`output_plan_steps.ts` 新增 `validate_required_plan_fields`——实例缺 port
  时返回 fatal（带可读指引「请向用户询问」），方案无法生成
- **移除自动选端口**：`assign_port` 删除「从默认端口起顺延选择空闲端口」分支；用户指定的
  端口原样写入，被占用由 Start 阶段报 PORT_BIND_FAILED
- **交互规则**：用户未提供端口时 Agent 必须先询问，禁止生成方案；文档（agent.md
  「监听端口的必填约束」、c4_asfp2_server.md §2.2）同步

## 用例 6：用户未提供点名/点描述✅

- **测试特性**：用户没有提供点名或点描述
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009。我们需要将这些数据转发到II区服务器上，目标地址是127.0.0.1:9900。
```

> 关键点：用户只提供了数据点**地址**（1000~1009），**没有提供点名/点描述**。

### 曾经出现的问题

LLM 在信息收集阶段自行发明了点名「点1000」…「点1009」（中文「点」+ 地址），
最终在执行模块 `merge_config_from_steps` → `handle_add` 的 `point.id` 校验中被拒绝：

```
自动执行失败: point.id "点1000" 包含非法字符，仅允许字母开头
```

根因：`point.id` 必须匹配 `^[a-zA-Z][a-zA-Z0-9_]*$`（字母开头，仅字母/数字/下划线），
而 LLM 发明的点名以中文「点」开头；且 `output_plan_steps` 的运行时强校验未覆盖
`point.id` 命名合法性，导致非法 id 一路漏到 merge 阶段才报错。

## 用例 7：对已接入设备追加数据点，新增点与已有点撞名

- **测试特性**：用户对已接入设备追加数据点，新增点名称与已有点名称冲突（撞名）
- **修复的版本**：（待填）

### 测试输入

前置状态：设备 `hnals_wt1` 已接入，含点 `windspeed`（addr=1000）。

```
给1#风机再追加一个数据点，地址2000
```

> 关键点：新增点的点名（LLM 翻译后）与已有点 `windspeed` 撞名，但 addr（2000）不同，属于另一个点。

### 曾经出现的问题

`handle_add` 的合并分支（`instance.id` 已存在时）按 `point_match_key`（writer 点用 `id`）匹配，
命中后是**覆盖**已有点的业务字段，而非去重。撞名且 addr 不同时，已有点 `windspeed` 的
`addr` 被静默改写成 2000，造成数据损坏且无报错。

期望：撞名时确定性去重（追加序号如 `windspeed_2`），仅当点的业务身份（addr 等）一致时才视为「更新」。
