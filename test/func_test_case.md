# C4 功能测试用例

> 本文件记录 C4 的功能测试用例，每条用例说明：**测试输入**、**测试特性**、**曾经出现的问题**、**修复的版本**。
> 用例对应「曾经暴露的缺陷」，用于缺陷修复后的回归验证。

---

## 用例 1：用户文本描述 ASFP2 接入与转发信息（内容齐全）✅

- **测试特性**：用户通过一条文本一次性提供全部接入信息——设备与协议、10 个点的「地址:点名」、接收监听端口（9001）、转发目标（127.0.0.1:9900）与转发点表（5000~5009）
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，转发采用asfp2协议，目标地址是127.0.0.1:9900，点表5000~5009。
```

> 关键点：点名、接收端口、转发目标、转发点表全部由用户提供，系统必须**原样采纳**——
> 不得自行编造转发地址、不得改动用户指定的端口，方案摘要须逐条列出「地址 ↔ 点名」映射与接收/转发端口供核对。
> 转发协议亦由用户明确提供（2026-09-05 起接收/转发协议逐侧必供——用户为接收侧声明的协议仅对接收侧生效，
> 转发协议缺失时 Agent 必须询问，禁止沿用接收侧协议或按转发目标描述推断）。

### 曾经出现的问题

C4H1 之前：转发点业务字段（addr）未采纳用户提供值，而是被系统自动编造（从 3001 起顺序编址）；
用户指定的接收端口在执行阶段未正确传递（`output_plan_steps` 首次调用因缺 ip/port 校验失败后重试）；
方案摘要不展示端口，用户无法核对。修复后：用户提供的点表、端口、转发点表原样进入 config.json。

## 用例 2：消息含与配置场站一致的场站名（归属校验）✅

- **测试特性**：条件完整，消息中的场站名「华能阿拉善风电场」与 agent.json 配置的场站「华能阿拉善」一致；用户文本完整描述接入与转发信息（点名、接收端口 9001、转发目标 127.0.0.1:9900、转发点表 5000~5009）
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入华能阿拉善风电场1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，转发采用asfp2协议，目标地址是127.0.0.1:9900，点表5000~5009。
```

> 关键点：消息带场站前缀「华能阿拉善风电场」，与当前场站一致 → 归属校验通过，直接接入；
> 不得因场站信息再次询问，也不得误判为「不属于当前场站」。

### 曾经出现的问题

C4H1 之前：LLM 在场站已设置的情况下仍反复询问场站名称与缩写（提示词两分支规则遵从性差，
且系统提示残留未替换的 `{{ current_site }}` 占位符，被模型解读为「场站未设置」）；用户另给场站名
（如「开鲁」）时被照单全收，违反「实例绑定唯一场站」。修复后：场站归属校验确定性执行——
场站已绑定时禁止询问，消息含一致场站名 → 直接接入，含其他场站名 → 回复「该资料不属于当前场站」。

## 用例 3：消息含与配置场站不同的场站名（归属拒绝）✅

- **测试特性**：条件完整，但消息中的场站名「华能通辽风电场」与 agent.json 配置的场站「华能阿拉善」**不同**；其余接入信息（点名、接收端口 9001、转发目标 127.0.0.1:9900、转发点表 5000~5009）齐全
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入华能通辽风电场1号风机的数据，第三方厂家通过asfp2协议给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，转发采用asfp2协议，目标地址是127.0.0.1:9900，点表5000~5009。
```

> 关键点：一个 C4 实例绑定唯一场站。消息场站与当前场站不同 → 必须回复「该资料不属于当前场站」并停止：

C4H1 之前：LLM 在场站已绑定时仍反复询问场站信息；用户另给场站名（如「开鲁」）时被照单全收并完成接入，
场站被静默切换，违反「实例绑定唯一场站」。修复后：场站归属校验确定性执行——
消息含其他场站名 → 直接回复「该资料不属于当前场站（当前场站：X）」并停止，不调用任何工具。

## 用例 4：转发点表描述模糊，Agent 多次询问与推断后接入（升压站）✅

- **测试特性**：新设备类型（升压站）；接收点表用「:」与「是」两种混述的松散文本给出（非表格）；**转发点表描述模糊**——仅说「点表与I区一致」，未逐点给出转发地址；Agent 通过多次询问与推断确定转发点表后接入成功
- **修复的版本**：C4H1

### 测试输入

```
现在需要接入升压站的数据，第三方厂家转过来的，asfp2协议，2390:电网频率，2391是正向有功，2392是反向有功，2393是正向无功，2394是反向无功，2395是uab，2396是ubc，2397是uac，2398是变压器油温，2399是环境温度。II服务器地址是127.0.0.1:9900，点表与I区一致。
```

> 关键点：转发点的 addr 是必要项，但用户仅以「与I区一致」的等价描述给出——Agent 必须通过
> 询问/推断明确每个转发点的地址（2390~2399 一一对应），**不得自行编造**；接收点表的松散文本
>（「:」与「是」混述）应被正确解析为 10 个点。

### 曾经出现的问题

C4H1 之前：转发点业务字段缺失时被系统自动编造（3001 起顺序编址），用户提供的等价描述
（「点表与I区一致」）无法被采纳。修复后：必要项缺失时 Agent 逐项询问，结合用户回答与接收侧
点表推断出转发点表（2390~2399 一一对应），多次交互后接入成功。

## 用例 5：未提供转发点表，用户以自然语言给出起始地址（升压站）✅

- **测试特性**：新设备类型（升压站），接收点表与用例 4 相同（2390~2399）；**未提供转发点表**，Agent 询问后用户以自然语言给出起始地址（「接收端口使用9001，转发地址/转发点表使用从一万开始的地址」，即转发 addr = 10000, 10001, …）
- **修复的版本**：C4H1——**经五轮迭代修复（见多轮测试记录与两节附录），2026-09-01 22:47 复测全链路通过**：
  Agent 先询问端口 → 9001 全程保持（摘要/工具参数/config.json/实际监听）→ 按钮确认执行 →
  服务监听 9001、采集/转发各 10 点；转发侧 127.0.0.1:9900 为用户显式指定，语义正确

### 测试输入

```
现在需要接入升压站的数据，第三方厂家转过来的，asfp2协议，2390:电网频率，2391是正向有功，2392是反向有功，2393是正向无功，2394是反向无功，2395是uab，2396是ubc，2397是uac，2398是变压器油温，2399是环境温度。将数据转发到II服务器的127.0.0.1:9900上，转发采用asfp2协议。
```

Agent 询问缺失信息后，用户补充回答：

```
接收端口使用9001，转发地址使用从一万开始的地址。
```

> 关键点：转发地址以**起始地址**的自然语言形式给出（「从一万开始」），Agent 应将其展开为
> 逐点 addr（10000~10009）并成功通过 `output_plan_steps` 生成配置。

### 多轮测试记录（C4H1）

| 轮次 | 修复状态 | 结果 |
|------|---------|------|
| 第一轮 | 初版 | ❌ Agent 陷入 `output_plan_steps` 反复失败重试循环（自省文字不断调整转发点对象结构：addr 位置、属性、字段顺序），接入失败。根因：转发点输入 schema 复用采集点定义，误要求 `name` 必填字段，无 name 的转发点被 Zod 校验拒绝 |
| 第二轮 | 修复①（校验错误可读化：带设备/点序/字段上下文）+ 修复②（点表完整性拦截：协议可判定时采集点必须逐点含业务字段） | ⚠️ 接入可用但不稳定：同一输入序列多次测试，LLM 传参**概率性丢失端口**——一次 9001 正确落地，一次被 registry 默认值 9000 静默覆盖（LLM 回复文本中复述了 9001，工具调用参数却未携带） |
| 第三轮 | L2 执行闸门（未经用户确认不执行）部署后 | ⚠️ 接入成功，但 **Agent 未询问确认**——用户回答「…从一万**开始**…」中的「开始」命中宽松确认正则，被状态机直接判定为已确认后放行执行 |
| 第四轮 | 按钮唯一确认通道部署后 | ⚠️ 方案摘要正确列出 9001，点按钮后 `output_plan_steps` 前两次因转发目标缺 ip/port 被可读校验拦截，**第三次重试 LLM 重建参数时把端口回退为 registry 默认 9000**（最终回复仍宣称 9001）。根因：端口仅存在于对话文本，确认轮注入的 deviceInfo 是端口回答**之前**抽取的（不含端口），重试时 LLM 手边只有提示词默认值 |

### 待决问题：用户确认方式 → 已定稿：Web 按钮为唯一确认通道

自由文本确认识别存在不可消除的歧义：参数回答与确认表达在文本上重叠（「从一万**开始**」命中确认词
「开始」）时，确定性状态机无法区分「提供信息」和「表达确认」——宽松正则下偶发跳过确认询问
（第三轮），收紧正则又会误拦正常确认（曾在第二/三轮间试验后移除）。

**定稿方案（已实现）**：使用 Web 技术确定用户确认方式——**用户点击按钮决定确认还是取消，
非按钮发送的内容一律不视为用户确认信息**：

- 前端 `ConfirmButtons`（方案展示句式触发展示）点击「确认」发送结构化消息
  `[C4_BUTTON_CONFIRM] 确认`，点击「取消」发送 `[C4_BUTTON_CANCEL] 取消，不执行`
- 后端执行闸门仅识别 `[C4_BUTTON_CONFIRM]` 前缀消息置位「已确认」；自由文本中的确认词
  （确认/好的/执行/开始等）不再构成确认，「从一万开始」类参数回答不会再误触执行
- 未确认时闸门拒绝执行，并提示用户点击「确认」按钮
- 协议契约记录于 web.md §3.1.3（按钮驱动）与 agent.md「执行闸门」，前端
  `useConfirmDetect.ts` 常量与后端前缀修改时必须两侧同步

### 第四轮修复：端口确定性捕获与注入（2026-09-01）

- **super_worker.ts**：新增 `userPort` 状态——从用户消息确定性捕获显式指定的接收端口
  （正则 /(?:接收|监听)端口…(\d{4,5})/，强制「接收/监听」前缀避免误捕转发端口；同场站名解析机制），确认轮注入
  「用户指定的数据接收端口: NNNN（必须原样使用，禁止改为默认端口）」，执行完成后复位
- **system.txt 解耦回归**：撤销曾硬编码的「默认接收端口 9000」字样——默认端口属于 asfp2
  MCP 注册 JSON 的 prompt_hints（运行时拼接），system.txt 保持服务中立，仅要求
  「写出具体数字、禁止含糊表述」并强调用户指定端口必须原样使用

### 设计变更：端口必填，无默认值（2026-09-01，用户裁定）

捕获+注入仍属概率性防线（LLM 仍可能忽略注入指令回退默认值）。据此将设计改为**釜底抽薪**：

- **不设置默认端口**（最终机制，字段级声明）：registry 中 `port` 字段**无 `default` 键**——
  必填语义由字段声明自表达；modbus port 删 502、iec104 port 删 2404 协议默认端口；
  config_schema.fields 进一步删除 `source` 维度（有 `default` 键=技术默认值自动填充，
  无=必填），L1 渲染「必填」、Zod 入参强校验原生生效
- **Agent 强校验**：`output_plan_steps` 的 `validate_runtime_input`（Zod）——实例缺 port/ip
  时报「缺少必要字段」（带设备/转发目标上下文），要求向用户询问，方案无法生成
- **必填项总定义**（用户裁定）：`point_schema.fields` 全量（点表）∪ `config_schema.fields`
  中无 `default` 键的项（配置），全部由用户提供、不设默认值；记录于 agent.md
  「必填项用户提供原则（无默认值原则）」
- **移除自动选端口**：`assign_port` 删除「从默认端口起顺延选择空闲端口」分支；用户指定的
  端口原样写入，被占用由 Start 阶段报 PORT_BIND_FAILED
- **交互规则**：用户未提供端口时 Agent 必须先询问，禁止生成方案；文档（agent.md
  「监听端口的必填约束」、c4_asfp2_server.md §2.2）同步

## 用例 6：用户未明确给出协议，Agent 推断协议但方案摘要未展示协议名 ✅

> **设计变更注**：协议推断已于 C4H1 后期整体移除（见用例 13）——本用例场景（消息无协议信息）
> 现行为改为**先询问用户协议**，而非推断。本用例保留为「推断时代的隐含确认缺陷」历史记录。

- **测试特性**：用户未在消息中明确给出通信协议——协议由 Agent 三层推断（点表字段 → 描述 →
  询问，见 agent.md「协议推断」）确定。设计规定「协议推断成功后不单独打断用户，协议作为方案的
  一部分在方案确认环节**隐含确认**」——隐含确认的前提是**方案摘要必须显著展示协议名**。
  实测摘要未展示协议，隐含确认落空
- **修复的版本**：C4H1——system.txt 方案摘要硬规则（逐设备、逐转发目标列出协议名）；
  2026-09-03 复测通过，方案摘要稳定展示「ASFP2 协议」字样

### 测试输入

```
现在需要接入1号风机的数据，第三方厂家给我们转来1#风机数据，10个点，从1000到1009，10个点分别是1000:风速、1001:功率、1002:风向、1003:桨叶角度、1004:发电机转速、1005:齿轮箱油温、1006:塔筒温度、1007:空气温度、1008:空气湿度、1009:大气压强，使用端口9001。我们需要将这些数据转发到II区服务器上，目标地址是127.0.0.1:9900，点表5000~5009。
```

> 关键点：消息**未出现任何协议名**（无 asfp2/modbus 等字样）——协议完全依赖 Agent 推断。

### 实测表现（C4H1）

- Agent 正确推断协议为 ASFP2（数据接收侧 asfp2_server + 转发侧 asfp2_client），接入最终成功
- **但方案摘要未展示具体协议名**——用户在确认环节看不到「本方案使用 ASFP2 协议」这一关键信息，
  推断结果实际上未经用户确认

### 风险说明

协议推断是概率性的（LLM 行为）。若某次推断错误（如把第三方转发误判为 Modbus TCP），
由于摘要不展示协议，用户在确认环节**无从发现**，会带着错误的协议完成确认——直到接入失败
（对端协议不匹配）才暴露，且用户难以定位失败原因。协议是接入方案的**核心正确性前提**，
必须进入用户的确认视野。

### 修复记录（C4H1，已实现待复测）

日志实证协议名展示为**概率性行为**：同一输入多次测试，部分摘要含「ASFP2 协议」（12:25 会话），
部分确认前摘要只写「数据转发协议」甚至不提（12:06 / 12:28 会话）——隐含确认因此落空。

- system.txt 方案摘要规则增补硬规则：**逐设备、逐转发目标明确列出通信协议名称**，
  禁止「数据转发协议」之类含糊表述
- agent.md「协议推断」块同步：隐含确认的前提 = 摘要展示协议名
- 可选加固（未实施）：`output_access_plan` 协议字段在前端方案卡片显式渲染

## 用例 7：文件上传点表接入，执行失败后跨轮修复被确认闸门拦截 ✅

- **测试特性**：通过文本文件上传点表接入（文件 → 解析 → 补充端口/转发信息 → 按钮确认 →

### 根因与修复

| # | 缺陷 | 修复 |
|---|------|------|
| 1【根因】 | 协议依赖 LLM 三层推断（点表字段→描述→询问），稀疏点表（仅 addr+点名）无法唯一确定协议，诱发错误猜测 | system.txt / agent.md 移除三层推断，协议改为用户必供；`declared_protocol` 动态关键词捕获（显式「X协议」模式 + 已部署协议名描述匹配），用户声明后禁止改用其他协议 |

此变更使协议退化为**确定性必填字段**：要么用户消息命中协议关键词（显式或描述），要么询问用户。
协议确定后 `output_device_info` 以 registry 的 `point_schema.fields` 对点表做完整性校验，字段缺失按
「协议错 / 点表缺字段可补 / 点表错」三态向用户诊断。转发协议（Reader）最初沿用目标→协议映射
（「转发到上级系统」→ asfp2、「入库」→ influxdb），2026-09-05 起该映射移除：转发协议与接收协议
逐侧必供、缺失必须询问（见用例 1 关键点与 agent.md §3.2 协议），禁止沿用接收侧协议或按目标描述推断。
实现上由 `output_device_info` 确定性校验兜底：存在转发目标而用户未声明转发协议时拒绝提交；
拒绝后进入问答握手——agent 复述候选协议向用户确认，用户答复含协议名或肯定复述即完成声明，
任意措辞（含联合声明「接收和转发都是用asfp2协议」）不会死锁。

## 用例 14：转发协议逐侧必供与问答握手（联合声明/非模板句式）✅

- **测试特性**：转发协议与接收协议逐侧独立必供——接收侧声明不算转发侧（「第三方厂家通过asfp2协议
  转来数据」仅提供接收协议，转发协议仍需询问）；转发协议声明分两条通道：
  **便捷通道**（模板句式「转发协议X」「转发采用/使用X协议」「用X协议转发」「写入X」）静默命中，
  无确认轮；**问答握手**（任意其他措辞）——`output_device_info` 拒绝提交一次，Agent 以是非题
  复述候选协议，用户肯定答复后放行。禁止按转发目标描述推断协议
- **修复的版本**：C4H1——2026-09-05 复测通过

### 测试输入与实测（2026-09-05）

场景 A：无协议信息的一句话接入（点表/端口/转发目标齐全，联合声明答复）

```
现在需要接入1号风机的数据，第三方厂家给我们转来1#风机数据，10个点，……使用端口9001。
我们需要将这些数据转发到II区服务器上，目标地址是127.0.0.1:9900，点表5000~5009。
接收和转发都是用asfp2协议。
对
```

> 实测：Agent 先分别询问接收/转发两侧协议（不推断）；联合声明不命中模板 → 闸门拒绝一次，
> Agent 以是非题复述「转发到II区服务器的协议是 ASFP2 吗？」→ 用户答「对」→ 放行，接入成功。
> 全程恰好一轮额外确认，无死锁。

场景 B：模板句式直接命中（同日早前会话）

```
监听端口9001，转发协议asfp2，转发地址和接收地址一致。
```

> 实测：便捷通道静默命中，无确认轮直接通过。

### 曾经的缺陷：握手缺失导致死循环（已修复）

初版确定性闸门仅扫描最新一条用户消息且无握手出路，联合声明「接收和转发都是用asfp2协议」
不命中四种模式 → `declared_forward_protocol` 永远为空 → 工具连续拒绝 7 次；用户四次肯定答复
（「对」「是asfp2」「是」「正确」）均无法推进状态，Agent 交替重复确认转发协议与转发点表映射。

| # | 缺陷 | 修复 |
|---|------|------|
| 1【根因】 | 声明判定依赖枚举用户措辞，自然语言无法穷举 | 放弃句式枚举的正确性职责，改为「双通道 + 问答握手」：便捷通道扫全会话累计消息（模板句静默命中）；权威通道锚定对话结构——闸门拒绝置握手态，Agent 是非题复述候选协议，用户答复含唯一协议名或肯定复述即完成声明（对复述的确认 = 提供） |
| 2 | 捕获仅扫最新一条消息，早前轮次的声明丢失 | 用户消息按会话累计缓冲（容量截断），被动扫描覆盖全部历史轮次 |
| 3 | 工具拒绝文案无提问指引，LLM 盲目重试 | 文案引导复述候选协议的是非题并禁止答复前重试 |

### 说明

用户表述不可枚举，但 Agent 的提问形态可枚举：开放问把答案空间压缩为「含协议名与否」，
封闭问压缩为是/否——表述多样性由 LLM 提问吸收，确定性由结构判定保证（agent.md §3.2 协议）。
任意新措辞的代价是恰好一轮复述确认，不会死锁。已知局限：用户在握手期间一句话出现两个协议名
（如同时纠正接收协议）时判定保持未定，Agent 继续提问，由用户明确后收敛；误声明的最终兜底是
方案摘要逐条列出协议 + 确认按钮。
